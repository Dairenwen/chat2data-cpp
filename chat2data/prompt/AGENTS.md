- **项目名称**：`chat2data`（Chat2Data）
- **项目描述**：面向自然语言数据查询的 C++ 项目，规划支持 Excel 和数据库分析及微服务协作。目前代码仍是开发骨架，提供命令行入口、核心库和测试；相关服务尚未实现。
- **开发语言**：C++17，禁用编译器扩展。
- **构建工具**：CMake 3.16 或更新版本。
- **测试框架**：CTest；现有测试为使用自定义检查函数的 C++ 程序，尚未接入 Google Test。
- **目标平台**：Linux 开发环境；其他平台以实际构建结果为准。

基本原则：

1. 优先理解项目现有架构、模块职责和代码实现。
2. 遵循项目现有设计，优先复用已有组件和工具。
3. 保持代码简洁、可读、可维护，避免过度设计。
4. 优先保证正确性，再考虑性能优化。
5. 未经要求，不主动添加额外功能或引入新的依赖。

## 2. 工作流程与修改原则

### 工作流程

1. **分析**：阅读相关代码，明确需求、修改范围及依赖关系。
2. **规划**：简单任务直接执行；复杂任务先说明实现思路及涉及的模块。
3. **实现**：按照既有架构完成修改，尽量减少影响范围。
4. **验证**：执行必要的编译、测试或静态检查。
5. **汇报**：简洁说明修改内容、验证结果及遗留问题。

### 修改原则

- **最小改动**：只修改当前任务必需的内容，不顺带重构无关代码。
- **保持兼容**：尽量保留原有接口、函数签名及外部行为。
- **保持风格**：遵循现有文件的代码组织方式，避免无关格式化。
- **保留注释**：保留准确、有效的原有注释，必要时同步更新。
- **控制依赖**：未经允许，不随意新增、升级或替换第三方库。
- **保护工作区**：不覆盖用户已有修改，不擅自删除文件。
- **版本控制**：未经明确要求，不主动执行 Git Commit、Push、Reset 等操作。

当用户只要求解释、分析或审查代码时，不主动修改文件。

## 3. C++ 代码风格

### 基本格式

- **缩进**：4 个空格，不使用 Tab。
- **大括号**：默认采用 Allman 风格，左大括号独占一行；修改已有代码时保持局部一致。
- **单行长度**：建议不超过 120 个字符。
- **头文件保护**：优先使用 `#pragma once`。
- **格式化**：如果项目提供 `.clang-format`，遵循其配置；目前项目中未发现该文件，修改已有代码时保持局部风格。
- **代码语言**：标识符使用英文，避免使用中文命名。

### 编码习惯

1. 优先使用标准 C++ 和标准库，避免不必要的第三方依赖。
2. 遵循 RAII 原则管理内存、文件描述符、Socket 等资源。
3. 根据所有权关系选择智能指针，避免无意义地使用 `shared_ptr`。
4. 合理使用 `const`、`constexpr`、`auto` 和引用。
5. 使用 `nullptr`，避免使用 `NULL`。
6. 优先采用清晰、直接的控制流程，避免过深嵌套。
7. 函数尽量保持单一职责，避免过长或过度拆分。
8. 不滥用模板、宏、继承和复杂设计模式。
9. 多线程代码应明确共享状态、锁的作用范围和对象生命周期。
10. 保持项目原有异常处理、错误码和日志机制，不允许未经批准擅自处理异常以及不必要的边界处理。
11. 代码书写标准规范，不应进行防御性编程。

### 代码组织

- 头文件主要存放声明、接口及必要的模板实现。
- 源文件主要存放具体实现。
- 按项目现有规则组织 `#include`。
- 不在头文件的全局作用域使用 `using namespace`。
- 优先使用已有工具函数，避免重复实现。
- 不为简单功能创建不必要的类或抽象层。

## 4. 命名规范

默认使用以下命名方式；已有模块采用其他统一风格时，优先保持局部一致。例如现有代码使用 `chat2data::run` 和 `print_usage`，不因此重命名。

| 对象         | 命名方式         | 示例                |
| ------------ | ---------------- | ------------------- |
| 类、结构体   | PascalCase       | `TcpServer`       |
| 函数、方法   | PascalCase       | `StartServer()`   |
| 普通变量     | snake_case       | `buffer_size`     |
| 私有成员变量 | _snake_case      | `_socket_fd`      |
| 函数参数     | snake_case       | `client_fd`       |
| 常量         | kPascalCase      | `kMaxConnections` |
| 宏           | UPPER_SNAKE_CASE | `MAX_BUFFER_SIZE` |
| 枚举类型     | PascalCase       | `ConnectionState` |
| 命名空间     | snake_case       | `network_utils`   |
| 文件名       | PascalCase       | `TcpServer.hpp`   |

### 命名原则

1. 名称应准确表达用途，优先使用完整、清晰的英文单词。
2. 避免 `data1`、`tmp2`、`func` 等缺乏语义的名称。
3. 循环计数器等局部场景允许使用 `i`、`j` 等简短名称。
4. 同一模块内的命名方式应保持一致。
5. 不随意重命名已有接口、变量或文件。
6. 布尔变量优先使用 `is_`、`has_`、`can_` 等表达状态。
7. 函数命名应体现行为，类命名应体现职责。

## 5. 注释规范

### 注释语言与风格

- **语言**：默认使用简体中文。
- **格式**：普通注释优先采用 `//`。
- **语气**：客观、准确、简洁，使用陈述句，不要使用否定句。
- **标点**：中文注释使用中文标点，技术标识符保留英文原文。
- **粒度**：重点解释关键逻辑、设计意图和特殊约束，不要兜圈子，直击重点。

### 注释原则

1. 注释重点解释**为什么这样实现**，必要时补充**如何实现**。
2. 对复杂算法、并发控制、资源生命周期和特殊边界条件添加注释。
3. 对容易理解的赋值、函数调用和简单判断，不添加冗余注释。
4. 保留已有有效注释，不随意删除、改写或统一格式。
5. 修改逻辑后，应同步更新已经失效的注释。
6. 不添加与代码实现不一致的注释。
7. 避免使用口语化、模糊或夸张的描述。

### 注释示例

推荐：

```cpp
// 使用 eventfd 唤醒事件循环，使其他线程提交的任务能够及时执行。
void Wakeup();

// 通过 weak_ptr 避免回调延长 Connection 对象的生命周期。
std::weak_ptr<Connection> weak_conn;
```

不推荐：

```cpp
// 调用 Wakeup 函数。
Wakeup();

// 定义一个整数变量并初始化为 0。
int count = 0;
```

### 函数与类注释

- 公共接口：说明核心功能、重要参数和使用约束。
- 复杂函数：解释关键执行流程和设计意图。
- 简单函数：函数名足够清晰时，可以省略注释。
- 类：仅在职责或使用方式不直观时补充说明。

除非项目已有相关规范，否则不强制使用 Doxygen 格式。

## 6. 文字与文档风格

### 文字表达

1. 默认使用简体中文。
2. 使用准确、专业、易理解的技术语言。
3. 优先采用简洁陈述句，避免冗长、重复的表达。
4. 尽量使用直接的肯定式表述，减少不必要的否定句。
5. 避免口号化、夸张性描述和无意义的修饰。
6. 类名、函数名、API、命令和技术术语保留英文原文。
7. 同一概念使用统一术语，避免反复更换说法。

### Markdown 规范

- 使用清晰的标题层级组织内容。
- 优先采用简短段落和必要的列表。
- 对比多个对象时，可以使用表格。
- 代码必须使用带语言标识的代码块。
- 复杂流程可以使用 Mermaid，简单流程优先使用文字。
- 避免无意义的分割线、装饰符号及重复标题。

### 项目文档

1. 文档内容应与实际代码保持一致。
2. 新增公共接口时，按需补充使用说明。
3. 不主动生成与任务无关的 Markdown 文档。
4. 不擅自重写 README 或已有技术文档。
5. 代码示例应使用项目真实存在的接口。

## 7. 回答风格与沟通方式

### 基本要求

- **语言**：简体中文。
- **语气**：专业、自然、直接、客观。
- **篇幅**：默认简洁，复杂问题按需展开。
- **结构**：先给结论，再说明关键依据或步骤。

### 回答原则

1. 直接回答用户问题，不添加冗余开场白或客套话。
2. 不重复用户已提供的信息。
3. 避免使用“显而易见”“非常简单”等评价性表述。
4. 不进行无依据的赞美、保证或夸大。
5. 不确定的结论应说明原因，不编造 API 和执行结果。
6. 技术解释应准确，优先结合项目实际代码。
7. 用户要求简短回答时，只保留核心结论与必要说明。
8. 用户要求详细解释时，按照整体作用、关键流程、核心原理的顺序展开。
9. 不主动输出大量无关示例和扩展知识。
10. 不在回答末尾机械地追加无关建议或提问。

### 代码输出要求

- 优先展示实际修改的关键代码。
- 不重复输出大段未发生变化的代码。
- 用户要求完整文件时，提供完整内容。
- 用户要求只修改注释时，不改变代码逻辑。
- 用户要求只解释时，不擅自修改实现。

### 任务完成汇报

完成代码修改后，默认采用以下格式：

**修改内容**

- 简要描述完成的功能或修复。

**涉及文件**

- 列出主要修改文件。

**验证结果**

- 说明构建、测试及检查结果。

若存在未完成事项或风险，再补充简短说明。简单修改可以合并为一段话，无需强制使用固定标题。

### 安全约定

1. 不擅自删除项目文件、数据库或用户数据。
2. 不擅自修改系统环境、服务配置或依赖版本。
3. 不在代码、日志中暴露密码、Token 和密钥。
4. 不执行未经授权的破坏性命令。
5. 不覆盖用户未提交的代码修改。
6. 遇到可能导致数据丢失或重大兼容性问题的操作，应先征求用户确认。
