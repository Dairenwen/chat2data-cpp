**系统身份**：你是一个资深的C++后端开发工程师，熟悉后端开发中业务逻辑实现。

**任务**：帮我完成用户子服务中会话管理以及用户相关的业务逻辑实现。

**要求如下**

1. 会话管理

   - 添加类`SessionManager`，包含在`chat2Data`命名空间中，负责管理会话信息。
   - 头文件`sessionManager.hpp`，源文件`sessionManager.cpp`，放置在`chat2data-cpp/chat2data/svc_userService`目录下
   - 类中包含`SessionData`指针，用于操作会话表和会话缓存。
   - `SessionManager`类中涉及操作：

     **创建会话**

     1. 接收用户 ID，生成密码学安全的会话 ID，构造 `SessionEntity`，将 `expiresAt` 设置为创建时刻加 3 天，时间单位为 Unix 毫秒。
     2. 调用 `SessionData::Save` 开启 MySQL 事务，插入会话并提交。提交成功后调用 `SessionData::DeleteCache` 使对应 Redis 缓存失效。
     3. 缓存失效成功后将会话 ID 返回给调用方。数据库写入失败时报告错误。若提交后 Redis 失效失败，则尝试在独立事务中删除尚未交付的会话，并报告失败。

     **通过会话 ID 获取会话信息**

     1. 调用 `SessionData::FindCache` 查询 Redis。命中且未到期时返回会话信息，命中但已到期时返回已过期。
     2. Redis 未命中时调用 `SessionData::Find(sessionId, true)`。在 MySQL 事务中按会话 ID 执行 `SELECT ... FOR UPDATE`，读取并锁定对应会话行。MySQL 和 Redis 均按原始字节匹配会话 ID。
     3. 会话存在且仍有效时，在持有行锁期间调用 `SessionData::SaveCache` 回填 Redis。TTL 取 3 天和会话剩余有效期中的较小值。回填步骤完成后提交 MySQL 事务并释放行锁。
     4. MySQL 中未找到会话时返回未找到，查询或回填期间到期时返回已过期。MySQL 或 Redis 操作失败时向调用方报告错误。

     **检测会话是否有效**

     1. 按上述流程获取会话信息，检查会话存在且 `expiresAt` 尚未到期。
     2. 有效时返回会话及所属用户 ID；不存在或过期时返回无效，依赖故障向调用方报告。
     3. 会话有效性以指定会话的存在和过期时间为依据，不能仅凭用户的在线状态判断。

     **通过会话 ID 删除会话**

     1. 调用 `SessionData::DeleteCache` 第一次删除 Redis 会话缓存。失败时重试一次，仍失败则报告错误并结束退出流程。
     2. 调用 `SessionData::Delete` 开启 MySQL 事务，直接按会话 ID 执行 `DELETE`。如果回填事务持有该会话的行锁，删除语句会等回填完成。删除语句执行后，会话行锁由删除事务持有至提交或回滚。
     3. 保持事务打开，等待 500 毫秒，再调用 `SessionData::DeleteCache` 清除可能在第一次失效后写入的缓存。Redis 删除出错时重试一次。
     4. 在用户退出流程中，第二次缓存删除成功后执行状态校正和用户缓存失效，再提交 MySQL 事务。删除、状态校正或缓存失效最终失败时报告错误，尚未提交的 MySQL 变更随事务回滚。Redis 中已删除的缓存由后续读取按需回填。
     5. 回填与删除由同一会话行锁协调。回填先拿到锁时，其写入在 MySQL 删除语句执行前结束，随后由第二次删缓存清理。删除先拿到锁时，等待中的回填查询要等事务结束，提交后会查不到已删除的会话。

     **获取指定会话 ID 对应的用户 ID**

     1. 复用会话有效性检测流程，从有效会话中读取 `userId`。
     2. 会话不存在或已过期时不返回用户 ID；依赖故障按错误处理。
   - 操作MySQL和Redis时必须符合Cache-Aside(旁路缓存)策略。
   - 过期时间：**3天**
   - 缓存策略：

     - 写策略：先写DB，删除Redis
     - 读策略：先查redis，未命中再查DB，查到后回填Redis
     - 删除策略：**采用延迟双删策略**。第一次删除 Redis 缓存在 MySQL 事务开始前执行，第二次在事务提交前执行。
2. 用户业务

   - 添加类`UserBusiness`，包含在`chat2Data`命名空间中，负责管理用户业务逻辑。
   - 头文件`userBusiness.hpp`，源文件`userBusiness.cpp`，放置在`chat2data-cpp/chat2data/svc_userService`目录下
   - `UserBusiness`类中涉及操作：

     **检测用户昵称是否唯一**

     1. 校验昵称输入，调用 `UserData::NicknameExists` 查询 MySQL。
     2. 根据查询结果返回可用或已存在；数据库错误单独报告。该检查不能替代注册写入时的唯一约束。

     **检测用户邮箱是否唯一**

     1. 校验邮箱输入，调用 `UserData::EmailExists` 查询 MySQL。
     2. 根据查询结果返回可用或已存在；注册时仍以数据库唯一约束为准。

     **用户注册**

     1. 校验昵称、邮箱和密码；**密码至少 8 位，数字、小写字母、大写字母和特殊符号中至少包含两类。**
     2. 检查昵称和邮箱是否已存在，调用 `Utils::GenerateUUID` 生成用户 ID，使用随机盐派生密码哈希。
     3. 构造初始状态为离线的 `UserEntity`，调用 `UserData::Save` 在 MySQL 事务中插入并提交。并发请求同时通过预检查时，由数据库唯一约束裁决，冲突返回注册失败。
     4. 提交后调用 `UserData::DeleteCache` 使用户缓存失效，再按协议返回注册结果。缓存失效失败时报告错误，已提交的用户记录仍保留。注册完成后由客户端发起登录。

     **密码登录**

     1. 接收协议中的 `nickname` 和 `password`；该账号字段可以是**昵称或邮箱**。
     2. 先调用 `UserData::FindByNickname` 查询 MySQL，未找到时再调用 `UserData::FindByEmail`；根据已保存的盐和哈希校验密码。
     3. 校验成功后通过 `SessionManager` 创建会话，并按下述“校正用户在线状态”流程更新状态、使用户缓存失效。全部成功后返回 `session_id`。
     4. 会话创建成功但后续状态校正或用户缓存失效失败时，尝试删除尚未交付的会话并按剩余有效会话重新计算状态。调用方收到失败结果。

     **获取验证码**

     1. 校验接收邮箱，查询 MySQL 并确认输入与注册邮箱完全一致，再生成六位数字字符串验证码和 `codeId`，保留验证码前导零。
     2. 构造 `CachedVerifyCode`，调用 `VerifyCodeData::Save` 写入 Redis，设置不超过 5 分钟的有效期。
     3. 通过 [notifyService.proto](../../proto/notifyService.proto) 中的 `SendVerifyCode` 调用通知服务。发送成功后返回 `code_id`，验证码仅随邮件发送。
     4. 发送失败时删除已写入的验证码并报告失败。

     **验证码登录**

     1. 接收邮箱、验证码 ID 和验证码；使用 `VerifyCodeData::Consume` 在 Redis 中原子校验并消费，不拆成独立的读取和删除。
     2. 分别处理验证码不匹配、不存在或已过期、Redis 失败；只有消费成功才能继续。
     3. 通过 `UserData::FindByEmail` 查找对应用户，并确认邮箱与已消费验证码的邮箱完全一致。随后复用密码校验成功后的会话创建、状态校正及失败处理流程。
     4. 验证码消费成功后，后续步骤失败时返回错误。客户端需要重新获取验证码。

     **会话登录**

     1. 接收已有 `session_id`，通过 `SessionManager` 检查会话及有效期。
     2. 会话有效时校正用户状态并使用户缓存失效，再返回登录成功。沿用原会话 ID 和过期时间。
     3. 会话不存在时返回未找到。会话已过期时**按下述自然到期流程校正状态**，再返回已过期。依赖故障按错误返回。

     **退出登录**

     1. 接收当前 `session_id`，先查询会话归属，以便删除后校正对应用户的状态。归属查询服务于用户状态处理，会话删除接口按 ID 直接执行 `DELETE`。
     2. 调用 `SessionManager` 执行延迟双删。第二次会话缓存删除成功后，使用同一个 MySQL 删除事务调用 `UserData::UpdateStatus`。该事务可看到本次已执行的会话删除，按其他有效会话计算状态。
     3. 校正状态后使对应用户缓存失效，再提交事务并返回成功。若无对应用户记录，完成会话删除即可。状态校正或用户缓存失效失败时，回滚会话删除和用户状态写入，并返回错误。

     **校正用户在线状态**

     1. 已注册用户的状态校正使用 `UserData::UpdateStatus`。退出登录复用删除事务，密码登录、验证码登录、会话登录和自然到期校正使用独立的 MySQL 事务。
     2. 在事务内按用户 ID 执行 `SELECT ... FOR UPDATE`，先锁定用户行，再查询该用户是否存在 `expiresAt` 大于当前 Unix 毫秒的会话。存在任一有效会话写入 `1`（在线），所有会话均已退出或到期时写入 `0`（离线）。
     3. 同一用户的状态校正争用同一行锁。每个请求拿到锁后再读取有效会话，使多个设备并发登录或退出时按实际剩余会话更新。用户缓存回填也使用该行锁，使先前读取的状态在写入方使缓存失效前完成回填。
     4. 独立事务提交后使用户缓存失效。退出登录则按上述流程在删除事务提交前使用户缓存失效。
     5. 会话自然到期后，在下一次校验该会话时查询其归属，并按其余会话校正用户状态。已过期的会话按无效处理。

     **获取用户信息**

     1. 接收 `session_id`，通过 `SessionManager` 校验会话并取得用户 ID。
     2. 调用 `UserData::FindCache` 查询用户缓存。未命中时调用 `UserData::FindById(userId, true)`，在 MySQL 事务中执行 `SELECT ... FOR UPDATE` 查询并锁定用户行。
     3. 查到用户时，在持锁期间调用 `UserData::SaveCache` 回填 Redis，再提交 MySQL 事务并释放行锁。
     4. 只返回 `user_id`、`nickname` 和 `email`。会话无效、用户不存在或依赖故障分别处理。

     **内部会话校验**

     1. 供 `IsSessionValid` 使用，调用 `SessionManager` 校验指定会话。
     2. 会话有效时返回 `valid = true` 和 `user_id`。会话不存在或已到期时返回 `valid = false`。到期状态校正或其他依赖操作失败时返回错误。
   - 包含成员：

     - `SessionManager`指针，用于操作会话信息
     - `VerifyCodeData`指针，用于操作验证码信息
     - `UserData`指针，用于操作用户信息
     - `SvcChannels`指针，用于操作RPC通道；当前类型定义在 `BreezeRPC.hpp` 的全局命名空间
     - 所有成员变量的初始化必须在`UserBusiness`构造函数中进行。但具体实例其他位置传入。

**注意事项**

1. 注册时只保存带盐的密码哈希，不保存明文或可逆加密结果。
2. 使用JSON进行序列化和反序列化，使用` BreezeUtil`封装好的的序列化和反序列化接口。
3. 程序中非法操作优先使用异常，异常信息和错误码在 `common/errorHandler.hpp` 中可以复用或增加。
4. 密码登录时，**username中可能是用户昵称，也可能是用户邮箱，如果能通过用户昵称获取到用户信息，就使用用户昵称登录；如果能通过用户邮箱获取到用户信息，就使用用户邮箱登录。**
